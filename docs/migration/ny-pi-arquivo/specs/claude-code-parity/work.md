# Paridade integral Claude Code → pi

## 1. Constituição e autoridade
Pedido do usuário: analisar TODOS os atalhos e comandos do Claude Code e replicá-los no pi. O usuário rejeitou explicitamente a entrega limitada aos equivalentes já disponíveis e, na clarificação seguinte, escolheu **incluir integrações dos serviços**. O escopo limitado de `docs/claude-code-compat.md` está **SUPERADO como critério de conclusão da tarefa integral**; sua implementação e evidências continuam válidas apenas para a primeira fatia.

Restrições preservadas: nunca inicializar Git/hooks fictícios; preservar o working tree concorrente; não ler/expor tokens; não reutilizar credenciais da assinatura em cliente substituto; não abrir acesso remoto/publicar sessões sem autorização específica; não mudar proteções por atalhos; nenhuma simulação pode ser marcada como paridade funcional. Desktop Linux não vira desktop compatível por apresentar uma URL. Uma sessão Claude separada não pode ser anunciada como a mesma sessão pi.

## 2. Especificação e aceite
- P1: WHEN cada atalho geral/contextual/Vim for acionado em seu contexto, THE SYSTEM SHALL executar seu comportamento real; diferenças verificadas mantêm o item pendente, não concluído.
- P2: WHEN cada comando da matriz for usado, THE SYSTEM SHALL executar o comportamento equivalente, incluindo argumentos/erros/cancelamento; um aviso de recurso ausente não satisfaz o aceite.
- P3: WHEN uma integração de serviço for solicitada, THE SYSTEM SHALL usar um contrato oficial e autenticação suportada, com fronteira de sessão explícita. IF serviço/conta/plataforma não permitir a operação, THEN o item permanece bloqueado, sem alegação de conclusão.
- P4: WHEN modos de permissão/teclas destrutivas forem acionados, THE SYSTEM SHALL preservar guardas, autorização, isolamento e limites existentes. Não há permissão para remover controles ou contornar políticas da organização.
- P5: WHEN a validação for executada, THE SYSTEM SHALL demonstrar cada comportamento por testes e aceite público isolado, incluindo falhas. Nenhum teste deve chegar ao modelo inadvertidamente; o fixture intercepta prompts inesperados.
- P6: A tarefa integral só será completa quando P1–P5 tiverem evidência para todo o escopo acordado. Não somar itens meramente documentados aos implementados.

## 5. Plano e interfaces
Escolher a menor arquitetura **após** resolver a fronteira de sessão dos serviços:
1. Contrato: fixar o que constitui paridade em integração externa; provar pré-requisitos de conta/plataforma sem abrir tokens.
2. Teclado geral: Shift+Tab e combinações Ctrl+X, com contexto, confirmação, timeout e preservação de copy/seleção. Não mapear ciclo de permissões para bypass indiscriminado.
3. Vim: ampliar estado do editor, movimentos, operadores, seleção, objetos de texto, registradores/repetição e desfazer, reutilizando primitives nativas quando equivalentes.
4. Comandos locais restantes: implementar por responsabilidade e atualizar matriz/consumidores; prompts de skills não são funções nativas e devem manter essa distinção.
5. Serviços: integração oficial autorizada, sem sessão falsa; autenticação pelo fluxo oficial, cancelamento e recuperação explícitos. Desktop continua bloqueado enquanto a plataforma não for suportada.
6. Validar uma vez por fatia integrada, com TDD obrigatório em bugs/fluxos críticos, cobertura por fonte, estrutura, E2E isolado e revisão; não declarar toda a tarefa concluída com uma fatia verde.
