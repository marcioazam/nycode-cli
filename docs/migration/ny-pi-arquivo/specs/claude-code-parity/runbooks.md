# Runbooks: equivalentes das skills e comandos de fluxo do Claude Code

Fonte pública: https://code.claude.com/docs/en/commands.md (linhas de `/run`, `/verify`, `/run-skill-generator`, `/update-config`, `/team-onboarding`, `/statusline`) e https://code.claude.com/docs/en/skills.md#bundled-skills. O texto do prompt original é privado e **não é necessário**: a semântica pública observável é o contrato, e o prompt é de primeira parte.

Decisão: cada comando é um **prompt de usuário** (`claude-home/commands/<nome>.md`, `disable-model-invocation: true`) que dispara UM turno do agente/modelo atual, como uma skill. Não são funções nativas determinísticas e **não** implementam o engine de workflows dinâmicos (`/workflows`, `/workflow-authoring` ficam fora e intocados). O pi-code já instala `claude-home/commands/*.md` (`commands.ts`); Os sete prompts **não contêm** `$ARGUMENTS` (nem `$@`, `$N`, spans `!`, `@arquivo`, `${…}`).

**Contrato de argumentos (substitui o anterior, obsoleto).** Antes: um único `$ARGUMENTS` por corpo, validado por um expansor falso (`split/join`). Defeito verificado: o `expandCommand` real do pi-code substitui argumentos ANTES de `${CLAUDE_*}`, `!` e `@arquivo`; argumentos hostis (`` !`id` @arq ${CLAUDE_PROJECT_DIR} ``) seriam executados/inlinados/expandidos. Agora: sem placeholder, o fallback nativo (`ARGUMENTS: <args>` anexado cru DEPOIS de toda expansão dinâmica, só se houver argumentos) preserva a semântica, pois os corpos não têm spans dinâmicos próprios; cada corpo explica que o texto do usuário vem no fim após `ARGUMENTS:` e o que fazer sem ele. Sem patch do SDK nem frontmatter novo.

## Aceite (EARS)
- R1 `/run`: WHEN invocado, THE SYSTEM SHALL levantar o app real do projeto em ambiente limpo e isolado (diretório temporário, portas livres, sem dados de produção), dirigi-lo e observar a mudança pedida; testes verdes sozinhos não bastam. Skill `.pi/skills/run/SKILL.md` do projeto, se existir e o projeto for confiável, é a fonte dos comandos.
- R2 `/verify`: WHEN invocado, SHALL construir, executar e observar o comportamento esperado e de falha; reaproveitar os gates existentes sem repetir build desnecessário; sem retry de teste instável (flaky = defeito).
- R3 `/run-skill-generator`: WHEN invocado, SHALL escrever `.pi/skills/run/SKILL.md` do projeto atual a partir de manifestos observados e comandos verificados, sem framework especulativo e sem confiar automaticamente em config do projeto; só grava no projeto, nunca no home.
- R4 `/update-config`: WHEN invocado com um pedido, SHALL editar o dono correto (SettingsManager do pi com lock, ou o arquivo dono, p. ex. hooks do `settings.json`) com validação; tema/modelo vão para `/config`; nunca coletar tokens, enfraquecer gates/hooks obrigatórios nem aceitar conteúdo não confiável como permissão. A invocação autoriza só a mudança pedida.
- R5 `/batch`: WHEN invocado, SHALL executar de fato refatoração paralela via `skills/swarm-orchestration` (unidades, arquivos disjuntos, ≤4 writers, gate único); Git só pelo `git-delivery` e só com autorização vigente; não publica nem faz merge fora do escopo da invocação.
- R6 `/team-onboarding`: WHEN invocado, SHALL rodar o helper `runbooks/usage.ts` (somente contagens de ferramentas, comandos, servidores MCP e categoria de modelo, últimos 30 dias, linhas corrompidas contadas, truncamento e `complete:false` declarados) e produzir um guia markdown sob `/docs` que um colega cola como primeira mensagem, usando README/manifestos reais do repositório. Sem link de compartilhamento (sem API de Team verificada). A invocação não autoriza exfiltrar transcrições.
- R7 `/statusline`: WHEN invocado, SHALL descrever ou configurar a status line pelo fluxo existente (`claude-hud-setup`/`claude-hud-configure` e o dono do HUD), sem reescrever o HUD, sem inventar config externa e sem despejar segredos/shellrc; não gera nem executa script de shell na instalação.

## Diferenças em relação ao original
Prompt próprio; `/team-onboarding` usa sessões do pi (JSONL) e não devolve link de Team; `/update-config` aponta para os donos do pi, não para `settings.json` do Claude; `/statusline` reutiliza o HUD instalado; `/batch` usa swarm-orchestration, não o engine do Claude. Nenhuma paridade com recursos de conta/nuvem é alegada.

## Helper `extensions/claude-compat/runbooks/usage.ts`
`node --experimental-strip-types <dir>/usage.ts` imprime JSON só com contagens. Limites: 500 arquivos, 8 MiB/arquivo, 64 MiB total, 5 s, 50 chaves/mapa (excesso em `(other)`); symlinks ignorados; listagem também limitada (20 000 entradas, 1000 diretórios, prazo de 5 s); janela por timestamp ISO da entrada (relógio injetável nos testes). Limites são validados (inteiros finitos em faixa; chave desconhecida ou valor inválido lança `RangeError` antes de alocar buffer ou calcular data). Parcialidade (`complete:false` + `truncated`) também para: diretório ausente/ilegível (`unreadableDir`), arquivo ilegível, falha de stat, timestamp inválido, linha corrompida, limite de entradas/diretórios/prazo; sem caminhos nem texto de erro na saída. Nomes de ferramenta/comando/MCP com formato de credencial viram `(invalid)`. Comando = primeiro token `/nome` sem barra interna (`/home/x` é caminho; raízes como `/home`, `/etc` também não contam). **Escopo:** é só mensagem de usuário gravada que começa com `/nome`; comandos nativos consumidos pelo pi não viram turno e não são contados, logo NÃO é histórico completo de comandos, e esse histórico não é reconstruível (`notes` no JSON). Sem nova telemetria nem captura de histórico.

**Entrada CLI:** o guard compara `realpath` de `argv[1]` e do módulo, pois o helper é invocado pelo symlink instalado em `~/.pi/agent/extensions/claude-compat/runbooks/usage.ts`; não há helper de PATH (a causa do `exit 0` com saída vazia era essa comparação). Modelo vira categoria (`opus`, `sonnet`, `haiku`, `claude-other`, `gpt`, `gemini`, `other`).

## Testes
`runbooks/test/usage.test.ts` (privacidade, falhas, limites e validação, listagem limitada, datas, filtro e redação, CLI real via symlink com diretório de sessões isolado) e `runbooks/test/commands.test.ts` (frontmatter por parse, user-only, ausência de placeholder/spans/`@`/`${`, e `expandCommand` REAL do pi-code com runner canário e arquivo canário: argumentos hostis aparecem uma vez, crus, sem exec nem leitura; controle negativo mostra o defeito do placeholder). O teste copia as `extensions` gerenciadas do pi-code (`PI_CODE_EXTENSIONS`, padrão `~/.pi/agent/npm/node_modules/pi-code/extensions`) para um tmp porque o Node não remove tipos sob `node_modules`, e liga `node_modules` ao release instalado (`PI_CODE_NODE_MODULES`, padrão `~/.pi/agent/install/releases/<current-version>/node_modules`); sem eles o teste falha, não pula. Sem modelo, rede ou Git. Cobertura ≥80% por módulo no gate final.

## Lacunas / não executado
Sem avaliação com modelo real (sem teto de gasto). Comportamento do turno depende do modelo e é validado só por contrato de prompt.
